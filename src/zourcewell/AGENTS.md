# zourcewell package

## Purpose

The importable package: configuration, the account pool, the HTTP surface, and
the three ways a person drives it (CLI, TUI, server-with-chat REPL).

## Ownership

Owned directly by this doc:

- `config.py`: `config.json` plus environment, `Settings`, `load_settings` / `save`, `ZOURCEWELL_*` resolution, `config._app_dir()`.
- `accounts.py`: the thread-safe account pool, rotation, cooldowns, one in-flight stream per account, runtime add/remove.
- `server.py`: `create_app`, kept as thin wiring that calls `register_routes(app)`.
- `server_routes.py`: every `/v1/*` handler plus `_check_auth` / `_pool` / `_prepare`.
- `server_concurrency.py`: the three shared executors (`_CHALLENGE_`/`_CLEANUP_`/`_STREAM_`), a local `_DaemonExecutor`, queued-slot acquisition, disconnect helpers, FastAPI lifespan, startup warmup. No completion logic.
- `server_runner.py`: bind-host resolution, port scanning, uvicorn Config/Server, readiness polling, shutdown.
- `cli.py`, `tui.py`, `tui_editor.py`, `chat_ui.py`, `chat_repl.py`, `dry_run.py`: the human-facing frontends.
- `__init__.py` (`__version__`, derived from the bundled stamp / `pyproject.toml`, never a literal), `__main__.py` (`python -m zourcewell`).

Completion mechanics, provider details and tool parsing belong to the children below, not here.

## Local Contracts

- Handlers resolve completion and stream entry points through a deferred `_server()` reference, so tests that monkeypatch them on `zourcewell.server` keep working. Keep that indirection.
- `__version__` is the one public version name. `zourcewell/__init__.py` derives it (the frozen exe's bundled `_version.txt` first, then pyproject `[project] version`, installed metadata, `"0.0.0"`), `server.py` / `dry_run.py` pass it to `FastAPI(version=...)`, `server_routes.py` reads it for `/health` and `/v1/models`, and `cli --version` prints it. `__init__.py` imports stdlib only, so a module-scope `from . import __version__` in `server.py` / `dry_run.py` / `cli.py` cannot cycle. Do not add a second literal.
- Request ceilings in `server_routes.py`: `MAX_REQUEST_BYTES` (8 MB, rejected with 413 before the payload is read), `MAX_TOOLS_PER_REQUEST` (128, 400, counted only when tools render), `MAX_ACCOUNTS` (64, 409, counted PER PROVIDER via `core.pools.accounts_for_provider` because that is what partitions the pool). `MAX_SECRET_CHARS` (4096) is enforced by `_reject_oversized_fields` on BOTH write routes, POST `/v1/accounts` and PUT `/v1/accounts/{identifier}/token`.
- Every error response carries the OpenAI envelope from `install_error_envelope`, which BOTH `register_routes` and `create_dry_app` invoke: the existing `detail` byte-identical PLUS `error` `{message, type, param, code}`. `_ERROR_TYPE_BY_STATUS` maps the statuses this surface raises and everything else is `api_error`; the middleware-side 413 (`_too_large`, outside the handlers) builds the same body through `error_envelope`. The 500 handler must NOT log -- Starlette's `ServerErrorMiddleware` re-raises after the body is written, which is what keeps uvicorn's traceback. `Retry-After` is sent only from a real horizon (`server_concurrency._retry_after_headers`, the soonest cooldown); a merely-busy pool carries none.
- Handlers never call `_prepare` / `build_models_list` inline: all four sites (live and dry-run `/v1/models` and `/v1/chat/completions`) hop through `asyncio.to_thread`, and `_prepare` still raises its 400/404 fast, before any account is touched. Inline, the opencode catalogue read (a blocking socket, up to ~30s while a managed serve boots) froze `/health` and every disconnect watcher.
- `_validate_messages` rejects a non-list `tool_calls` with a 400 naming the field: the prompt render iterates it, so a scalar or object surfaced as an opaque 500. Non-dict ELEMENTS stay accepted (the renderer skips those).
- `build_models_list` entries carry `thinking` / `search` as extra top-level keys (resolved from the live spec; `False`/`False` when it could not be), the only way a client learns whether the toggles are honored for that model. `/health` carries `providers`, a per-provider `{accounts, accounts_with_token, banned}` map computed from `settings.accounts` alone -- no pool construction, so `/health` stays side-effect free.
- A pool is built only from accounts bound to its own provider. `server_routes._pool` has no cross-provider fallback: an unregistered or empty-bound provider id gets an EMPTY pool and a 503 that names it. The old unfiltered `list(settings.accounts)` fallback handed provider X provider Y's credentials (a Qwen ES256 JWT replayed to chat.deepseek.com). A registered provider with zero bound accounts is a 503, never a silent borrow — the rule `_reject_unknown_provider`, `accounts.usable_provider` and `tests/test_live_smoke.py` already followed. The account ROUTES add an edge check on top: an explicit `provider` must be ACTIVE, not merely registered (`_reject_inactive_provider` 400s it naming the active set), because a non-active id otherwise landed in the SELECTED provider's pool, which then served it as its own. Token set and delete are provider-SCOPED (`pid or pool.provider_id`, resolved before removal): one identifier can exist once per provider, and the unscoped first match mutated the other provider's record.
- The non-stream chat route's catch-all converts any non-`HTTPException` provider failure (deepseek/client.py's `create_session` / `pow challenge` RuntimeErrors) into a scrubbed 502 and a scrubbed `logger.warning`; `_StreamCancelled` and `HTTPException` keep their own statuses. Without it uvicorn logged the traceback with the raw upstream body.
- `_TOKEN_SHAPED_RE` is `^[A-Za-z0-9_.=-]{32,}$` (the bearer/JWT alphabet, so dotted JWTs and a trailing `=` are refused too). Every identifier route refuses it with 400 ahead of the API-key check and never echoes the value. A URL reaches access logs, proxy logs and `Referer`, so this is what stops a 64-char bearer token from being handed back through an old 404 detail. The same rule covers error text: `AccountPool.add`'s duplicate `ValueError` names `email`/`mobile` only, never `AccountConfig.identifier` (`token[:10] + "..."` for a token-only account), because it becomes the 409 detail verbatim.
- The request access log is off on all three serve paths (plain serve, server-with-chat, dry run). uvicorn's error log is unaffected and redacts what it prints.
- `GET /v1/waf/status` requires the API key because its payload names absolute binary and profile paths, and `GET /v1/models` carries the same gate — it was the one `/v1/*` route anyone on the bind could read unauthenticated. `GET /health` stays unauthenticated on purpose so existing pollers keep working.
- `"keys": []` means auth disabled, and a non-loopback bind prints a startup warning naming the bind, what is reachable, and how the gate reads. Keep the warning; it is the only warning between the operator and a LAN-visible unauthenticated API.
- `max_retries` is clamped 0-5 at load. With `ZOURCEWELL_MAX_RETRIES` unset the clamp is runtime-only and a hand-edited value survives a save; with the env var set the clamped number is written back.
- `Settings.save()` holds `_CONFIG_SAVE_LOCK` across the whole read-modify-write: the accounts SNAPSHOT and the file write are one critical section. Locking only the write loses records — two mutators each persist a payload built from a list one has already outgrown, so config.json stays valid JSON and silently drops an account. The lock is a plain `Lock`, so `save()` acquires it exactly once; never nest a second `with _CONFIG_SAVE_LOCK` inside it.
- `load_settings` validates the configured `provider` and every `providers` entry against `core.registry.registered()` and an unknown id is WARNED ABOUT BY NAME (with the file and the known ids) before falling back to `deepseek`. It is a loud refusal, not a raise: `load_settings` is the shared entry point of serve, dry-run, the TUI and the CLI, and one mistyped letter must not make the server unstartable. Same "name it in the log instead of blocking recovery" rule as `accounts.usable_provider`. A registry that cannot be imported (`_registered_provider_ids()` returns None) leaves the ids alone.
- `config._app_dir()` returns `Path(sys.executable).parent` when frozen, so a shipped exe reads and writes `config.json` next to the binary; otherwise repo root ONLY when a `pyproject.toml` sits beside it (a wheel's `PACKAGE_DIR.parent.parent` is the interpreter's `Lib/`, admin-only and wiped by a venv rebuild), else the per-user dir (`%APPDATA%` on Windows, `$XDG_CONFIG_HOME` / `~/.config` on POSIX). `ZOURCEWELL_DATA` follows the same base for its `data` default. `dist/` doubles as the frozen app's credential store; full rationale in `ARCHITECTURE.md`.
- A present-but-empty (or whitespace-only) `ZOURCEWELL_*` / `OBSCURA_*` env var counts as ABSENT and `config.json` decides: the rule is module-wide in `config.py` (`_env_str`, the `_bool` / `_int` / `_str` / `_text` closures, `active_account`, `browser_bin`, `_providers_list`, the import-time `ZOURCEWELL_DATA` / `_env_dir`), not local to one helper. A shell profile exporting `KEY=` would otherwise silently revert each field to its built-in default.
- `cli.py` and `chat_ui.py` keep thin re-exports of names that moved into `chat_repl.py` and `server_runner.py`, because tests and the TUI import the historical names from there. Do not drop a re-export without fixing its importers first, and do not add one without an importer. `cli` re-exports `_is_port_free` / `_next_free_port` / `_ensure_free_port` / `_run_server` / `_resolve_bind_host` from `server_runner`; `chat_ui` re-exports the `chat_repl` helpers and the `server_runner` bootstrap; `tui` imports only `_read_interactive` from `tui_editor` at module scope. `_stdin_is_tty` is a bare module-scope import from `tui_editor`, not a re-export, so the 7 test sites that patch `cli._stdin_is_tty` by name keep working.
- `_upsert_account`/`provider_is_registered`: a `--provider` on `login`, `serve` and `chat` must name a REGISTERED provider, not merely match `^[a-z0-9-]+$`. The shape check is not membership, and the gap opened a ~30s DeepSeek Obscura window for `login --provider glm` and then stored DeepSeek's `userToken` under `glm` -- an account no UI lists and no request can serve. `cli` refuses with exit 2 and `_unknown_provider_exit` (the one wording all three share); `tui._offer_auto_login` cannot exit, so it refuses in-app and returns the usual `("", False, 0.0)`. `deepseek` is exempt: its login IS the direct browser path, not a registry entry point. Only the FLAG is checked, never `settings.provider` (a hand-edited config id is normalized in `_upsert_account`).
- `tui._ask_account_provider`'s empty/EOF answer must land INSIDE the active set: the multi-mode default is `"deepseek" if "deepseek" in active else active[0]`, and single mode coerces the inherited selection through `accounts.usable_provider`. It used to return the literal `"deepseek"`, so with `providers=["qwen","opencode"]` one Enter filed the new account under a provider that is not active -- no pool builds from it and no request can serve it (the `login --provider glm` class). An explicitly typed id is the operator's choice and stays verbatim.
- `login --provider <id>` pins the DRIVER: `--provider deepseek` travels as the 4th arg of `_obscura_login_token`, so the call cannot re-resolve `settings.provider` (a config set to qwen once sent the credentials to the Qwen signin); every other id goes through `registry.get(pid).login`. The flag-less call keeps the settings-driven 3-arg form, and the token is always stored under the provider that produced it.
- A non-DeepSeek login that raises (opencode's `login` raises by design, a failed Qwen signin) or resolves to no registered provider FAILS CLOSED in `cli._obscura_login_token`: the reason is reported as the login detail, the command exits 3, nothing is stored. The DeepSeek browser driver must never run for another pid -- the old bare `except: pass` fell through to it, opened a ~30s chat.deepseek.com login and filed DeepSeek's `userToken` under the other provider.
- A successful relogin over a record with `banned` / `banned_until` set prints the `accounts unblock <email>` hint and never clears the marker: the pool keeps skipping the account, a suspended account can complete a login, and `accounts unblock` (CLI or REST) is the only clear.
- The TUI's ban hint refines the login page's horizon the same way `cli.cmd_login` does: `tui._offer_auto_login` probes `accounts.check_ban_for_token(token, provider=_pid)` (the bare form only for deepseek, so a Qwen token is probed as Qwen) and prefers the probe's expiry over `parse_ban_until(ban_detail)`. Best-effort, never fatal.
- Account mutations are provider-SCOPED wherever an identifier is typed: CLI `accounts set-token` / `remove` take `--provider` (default = the pool's `provider_id`, i.e. an explicit id, else a member's `provider`, else `deepseek`), and the TUI's typed-name set-token / delete paths scope through `_provider_scope`'s single id. One identifier exists once per provider (`config.account_identity`), so the unscoped first match survives only for a blank multi scope -- it mutated (or deleted) the OTHER provider's record.
- `cli._port_number` validates `--port` at parse time (1-65535; the argparse default stays 0 = absent). `server_runner._ensure_free_port` is the ONLY coercion point: an out-of-range or non-numeric value warns and scans from 5001; `_run_server`, chat_ui and dry_run pass the raw value through. This matters because `socket.bind` raises OverflowError for a bad port -- not an OSError -- and it escaped `_run_server`'s KeyboardInterrupt handler as a traceback (it killed the TUI menu).
- `cli._save` wraps `settings.save()` so a refusal (unparsable config, unwritable location) prints one line instead of a traceback, and every mutating command turns the `False` into exit 1; `cmd_login` returns 3 and still prints the fresh token, because a ~30s browser authorization is not repeatable on demand. Its TUI twin is `tui._select_provider`: a `RuntimeError`/`OSError` from `settings.save()` prints one `_err` line and keeps the in-memory pick (the serve gate continues), where the traceback used to kill the TUI.
- Both frontends print a non-empty no-token login detail (a ban hint or the driver's reason) as `Evidence: …`, capped at 300 chars: `cli.cmd_login` and `tui._offer_auto_login`.
- TUI login persistence mirrors `cli.cmd_login`: `tui._login_token_expiry` reads the Qwen JWT `exp` (`providers.qwen.auth.jwt_exp`, non-DeepSeek only, 0.0 = unknown) because the registry `login()` seam returns the legacy 3-tuple and drops the signin expiry. The add path stores it as `token_expires_at` (a TUI-added Qwen account kept 0.0, so the proactive re-signin could never fire) and carries the login result's `banned`/`banned_until` straight into `AccountConfig` -- it used to scan `settings.accounts` for the email, which on this path matched nothing, so the screen promised a ban the saved record never got. The set-token path writes a KNOWN expiry only, never erasing a persisted one.
- `server_concurrency._startup_warm` gates the shared Obscura warmup (CHAT_HOME / DeepSeek host) on `needs_waf_jar` for any active provider, then still runs every active provider's own `warmup()`. The lifespan applies `_effective_log_level(settings)` = `_runtime_log_level` (runtime) > `log_level` (saved) > INFO; chat mode sets and restores only the runtime attr, because any in-session save would persist a saved-field override.
- `cmd_chat` dispatches through `Provider.complete`, never a provider module's engine. It serves `--provider qwen` / `opencode` too, and calling DeepSeek's `_complete_with_failover_sync` there ran DeepSeek's whole path for every provider -- it closes over its own module globals and never reads `prep["provider"]`, so a Qwen ES256 JWT went to `chat.deepseek.com` as a `userToken`. `complete` (not `complete_request`) is the seam because `cancel_event` defaults to `None` there and every provider forwards it to its OWN `_complete_with_failover_sync` as a keyword, which keeps same-request ban failover and every existing engine-seam test double working. `cli` must not import `providers.*.completion_service`. Both chat branches (accountless local provider and pool-backed) funnel every `Exception` into one `_chat_fail` line -- one actionable message plus the provider's token hint, exit 1 -- because a one-shot command's raw traceback IS the whole UX and can reprint an upstream body; only `Exception` is caught, so Ctrl+C still propagates.
- Both chat frontends gate a start on provider-SCOPED accounts: `chat_repl._scoped_accounts` resolves `core.pools.providers_requiring_accounts(settings)` (an empty registry answer falls back to every active id, the same conservative rule as `tui._preflight_reason`) and counts through `accounts_for_provider`; `chat_ui` reuses it and names the scope in the refusal. Counting the GLOBAL `settings.accounts` let a single-qwen config with only a DeepSeek account on file pass preflight and then 503 every request, because `server_routes._pool` has no cross-provider fallback.
- `tui.py` imports only `_read_interactive` from `tui_editor` at module scope and must not gain more of its internals as module attributes; anything else it needs from there (`_ensure_vt`) is imported inside the function that uses it. For the same reason `tui` imports `cli.provider_is_registered` / `cli._unknown_provider_exit` INSIDE `_offer_auto_login` rather than at module scope. `tui._normalize_provider_choice` is a pure delegate to `cli.normalize_provider_id` via an in-function import, tui defines no alias map, and a provider's human label comes from `accounts.provider_label`, never a local copy.
- Chat REPL dispatch accepts exactly the commands `_print_help` / `_print_multi_help` list; `tui.main_menu` accepts its on-screen choices verbatim (digits, `q`) plus the literal `dry`. Quit lives one level down: `q. Go back` opens the chooser, whose `q. Quit` quits the serve (Ctrl+C/EOF on the menu prompt quits directly).

## Work Guidance

- The three shared executors are `_DaemonExecutor`, not `ThreadPoolExecutor`. `ThreadPoolExecutor` has no daemon option -- `initializer` runs inside the worker after it is started, and `Thread.daemon` refuses to change on a live thread -- and `Thread.__init__` inherits the SUBMITTER's flag, so worker daemon-ness was decided by an accident. `_DaemonExecutor` is built from two public pieces (`concurrent.futures.Future` + `queue.SimpleQueue`) and offers only `submit`, because that is all the three call sites use. Reaching past that (overriding `_adjust_thread_count`, importing `concurrent.futures.thread._worker`) is exactly the private coupling to avoid. The flag is deterministic but NOT sufficient on its own: `concurrent.futures.thread._python_exit` joins every worker it created, daemon or not, so a worker parked in an uninterruptible C call is ended by `core/transport.py`'s bounded read (both web providers), not by the flag.
- Keep the layering as it is: thin `create_app`, routes in `server_routes.py`, the completion engine in the owning provider, mechanics in `core`.
- Both TUIs and the REPL are stdlib-only and Windows-safe (plain `input()`, no curses). Keep it that way; `serve` has to work without a third-party terminal library. `tui_editor` is the lowest-level terminal module: it imports nothing from `zourcewell`, so it may own shared terminal probes (`_stdin_is_tty`, `_ensure_vt`) that `tui.py` and `cli.py` reuse.
- The settings menu in `tui.py` declares its 17 rows in one table (`_table()`), read by both the draw and the dispatch. Never declare a row twice: that is how setting 2 came to read "WAF warmup at startup" to the toggle and "Warm up WAF at startup" on screen. Rows 1-17 plus "18. Back" are what the tests drive, so edit a row in place instead of renumbering.
- `_provider_scope()` is the single provider-scope lookup (`active_ids`, `is_multi`, `single`). Five screens used to spell it out separately and drifted; `accounts_menu` and `main_menu` additionally scope their account list through `single`.
- A menu row never calls `models()`: opencode's `models()` reads its serve and BOOTS the managed instance when nothing answers, so no screen may pay a boot (or a dead-base connect) for a list; a catalogue a menu does need comes from `Provider.models_hint()`, which does no I/O (the last read else the static fallback), and may therefore be older than `models()`. `models()` stays the live view for `/v1/models`, `zourcewell models` and warmup. Provider rows (`_select_provider`) are a label and nothing else: no id and no current marker (the main menu header is where the active mode is read; the chooser asks the question fresh every time), no model count (that was a catalogue read per row) and no account/token tally (the start preflight names a missing token when it actually blocks a start).
- OpenAI parameters the web upstreams cannot honor are accepted, ignored, and logged once per request; the warn-and-drop set includes `logprobs` / `top_logprobs` / `seed` / `logit_bias`, which are a silent drop no longer. `tool_choice` honors `auto` and `none`; a forcing value is warn-and-drop.
- This folder owns one sink of the scrub contract: the non-stream chat route's catch-all (see the bullet above). It scrubs the reason TWICE -- once into the `logger.warning`, once into the 502 detail -- before truncation, because the failure never reached the terminal ladder. `core/AGENTS.md` owns the rest of the contract and the full list of sinks; check that list before adding a new one here, and never echo an upstream body from `server_routes.py` without going through `core.engine.scrub_upstream_text`.

## Verification

- `python -m pytest -m "not live" -q` from the repository root. Every change here needs it green.
- `python -m pytest -m live -q` after a change to a route, a limit, or a wire format.
- `python -m zourcewell serve` on a loopback bind is the manual smoke check for a routing or lifespan change.
